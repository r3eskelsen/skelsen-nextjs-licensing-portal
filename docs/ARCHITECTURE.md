# G0 — Architecture and scope

## Decision

Choose **local Supabase**, not a custom PostgreSQL/auth reimplementation. The full local stack provides an actual RLS/Auth integration target without cloud expense; it does require a compatible container engine. A fallback PostgreSQL-only imitation would not demonstrate Supabase Auth or hosted parity and is therefore excluded from the current portfolio claim.

## Trust flow

Browser → Next.js App Router / server actions / import route → per-user Supabase session → PostgREST → PostgreSQL RLS → organization rows.

Auth sets identity. Memberships determine each user's assigned organization and role (`client`, `admin`, `owner`). RLS evaluates membership on every query. A v1.0.1 additive migration limits membership SELECT to the authenticated user's own row, avoiding disclosure of other members' IDs/roles. The dashboard also scopes its query to the signed-in user and hides admin actions for clients; UI-only checks are never the authorization boundary. Login and registration use a local development account only. Audit events are generated by a database trigger for license creation.

## Data model

Organizations 1:N memberships 1:1 auth.users; organizations 1:N licenses, documents, renewals and audit_events. License-linked tables have composite tenant foreign keys. Documents currently store metadata only and do not implement file uploads or storage permissions. Renewals are tracked in schema, not editable in UI.

## Role matrix

| Action | Client | Admin | Owner | No membership |
| --- | --- | --- | --- | --- |
| View own org and licenses | Allow | Allow | Allow | Deny |
| Create/update own org licenses | Deny | Allow | Allow | Deny |
| View another org | Deny | Deny | Deny | Deny |
| Modify memberships | Deny | Deny | Deny | Deny |
| View own organization audit | Allow | Allow | Allow | Deny |

Owner is an organization-level role, not a global superuser. No client-facing delete/update membership workflow is implemented.

## Acceptance definition

A release is **verified** only if local schema migrations load cleanly, positive/negative RLS cases are executed with at least two distinct authenticated users and two organizations, denied requests return no unauthorized records, and the Next.js build plus browser tests pass. Document actual command output in `evidence/`, label HOLD when blocked.

## G0 risk assessment

| Risk | Impact | Mitigation / gate |
| --- | --- | --- |
| Docker or port collision | High | G1 read-only system inventory; localhost-only stack |
| Privilege escalation across tenants | Critical | RLS, foreign key boundaries, negative runtime cases G3 |
| Auth session misconfiguration | High | Test refreshed credentials, logout and unauthenticated redirects G3 |
| Unsafe spreadsheet imports | High | CSV restrictions + test invalid inputs; defer Excel |
| Publishing sensitive logs | High | Scrub logs, inspect diff, secret scan G4 |
| Version drift | Medium | Install dependencies, generate `package-lock.json`, commit only after G2 |
| Misleading commercial claims | High | Explicitly keep unverified status until G3 and G4 |

## Constraints

Local testing only; no QNAP, VPS, client production systems, GPU, external API spend, or unrelated Docker resources. No artificial screenshots or falsified logs.
